# FS-001 — Bootstrap Plan

## Intent and governing boundaries

This Plan realizes `functional-set.md` at Design revision `12e71d53fde329b16b14ed8103136443696efa70`. Build, Manage, and Install remain distinct authorities. Bootstrap construction roots are temporary and must not become an alternative permanent package format or package-management authority. A definitive Build chroot is created by Manage from Distro-produced packages, not by copying the temporary chroot. M3 proves native production and complete rebuilding of the definitive managed Build-chroot package closure; M4 publishes the bootable collection and preserves native Build/Manage capability. M5 independently boots that collection and proves Distro can act as the foreign host for fresh M1→M2 self-replication.

## Technical realization by milestone

### M1 — Cross-toolchain

**Result and boundary.** M1 produces a validated Distro-targeting cross-toolchain, target headers and C runtime interface sufficient for M2. It is not the definitive Distro Build chroot or an installed system. Its construction may use explicitly declared Arch host tools, but exported target components must be distinguished from host inputs.

**Host qualification.** On the initial Arch Linux host, record architecture and kernel information, required build utilities and their executable versions, compiler/linker capability, and potentially contaminating build environment settings. Qualification shall separately establish (1) tool availability and working C/C++ compile/link probes, (2) compatibility with the chosen target interfaces, (3) the ability to execute the chosen isolation arrangement including mount and permission behavior, and (4) availability and verification of resolved upstream sources. Fail with actionable deficiencies; never install, upgrade or remove host packages. Minimum host/kernel versions shall be justified by observed compatibility results, not assumed from package presence or prototype constants. The same qualification and construction workflow must also be executable on the installed Distro VM acting as a new bootstrap host in M5. Keep host-package version detection and other distribution-specific probes behind explicit host adapters; neither the M1 build logic nor source resolution may require `pacman` when running on Distro.

**Source selection and restart identity.** Before starting M1 cross-toolchain construction, resolve the complete initial bootable bootstrap manifest, including all selected M1–M5 packages and their build/runtime dependency closure, and qualify the entire installed host package/version baseline in one preflight. For each selected package or source-providing component, establish its installed host counterpart, preserve its full distribution version, derive an upstream-version candidate, and confirm that the corresponding upstream release is resolvable. Missing, ambiguous, or unresolvable entries block M1 until the user remedies the installed host or the manifest/mapping is reviewed; bootstrap never modifies host packages. The host adapter resolves split packages and source-to-output relationships explicitly, without substituting a capability-only or fabricated version. This qualified version baseline is fixed for the execution. On Arch, read installed versions with `pacman -Q` and parse optional epoch and trailing `pkgrel` without treating the result as automatically verified upstream source identity; on Distro, use Manage installed state. Source archives need not all be downloaded at preflight: authenticate, verify and lock each chosen source artifact **incrementally when first consumed**, using the already-qualified version baseline. Resumption cannot silently requalify changed host versions or alter source locks; changed package requirements or baselines require a new full preflight execution. No persistent bootstrap-version catalog is created.

**Host-write protection and target contract.** Select one initial target architecture, target triple, Linux ABI and GNU C library strategy as a *Planning* contract before dependent toolchain construction. The prototype's `x86_64-distro-linux-gnu` is evidence, not yet an accepted selection. Through completion of M2 self-replication, use **Bubblewrap only** as the bounded host-write protection arrangement primarily to protect the host filesystem against accidental writes: host system paths are read-only and only named workspaces and target roots are writable. Specify allowed host tools/libraries, mounts, environment, UID and privilege behavior, and cleanup. Do not silently fall back to elevated or unrestricted execution if those protections cannot be established. Inspect actual host-versus-target dependencies separately; host-write protection alone does not establish native independence.

**Construction.** Build the target assembler/linker, initial compiler, Linux API headers, C library interface, and necessary compiler/runtime finalization in an explicit dependency order. Keep the toolchain installation root and target sysroot distinguishable; declare each intermediate host dependency and each input carried forward to M2. The cross-toolchain need not be made into a final Distro package in M1.

**Acceptance and M2 handoff.** Require fresh-workspace construction and inspect compiler driver configuration, target triple, search paths, generated ELF interpreters and dynamic-library closure. Run representative target C and C++ compile/link/execute probes in a suitable isolated target context, including a negative contamination case. Verify that observed dependencies match the declared intermediate foreign-host allowances and that M2 will use the intended target headers, linker and libc, rather than silently taking them from the Arch host. Record machine-readable qualification, selected source identities/digests, build input and environment, toolchain output inventory, probes, failures, and restart evidence. M2 begins only after these checks pass.

### M2 — Temporary tools

**Result and boundary.** M2 delivers a temporary, Distro-native-capable build environment that can **reproduce its entire required temporary toolchain and userspace closure**. It is not the definitive managed Build chroot or an installed Distro system. M2's first generation may use the validated M1 cross-toolchain and explicitly declared foreign-host assistance; M2 acceptance is based on native self-replication, not on the ability to execute a shell or compile one sample program.

**First-generation construction.** Import the verified M1 handoff and construct generation A in a distinct temporary root, keeping installed files separate from sources, workspaces, scripts, logs and completion records. Select the complete native shell, compiler, assembler/linker, build utilities, headers, libraries, and other capabilities needed to reproduce the M2 environment and support M3. Derive source identities from the current bootstrap execution's verified inputs rather than hardcoded prototype version pins. Declare all foreign-host tools and permitted intermediate construction dependencies.

**Native chroot readiness and transition.** Before ceasing the pre-chroot host-write protection, verify that generation A can execute its native shell, dynamic loader and shared-library closure, essential filesystem utilities, and the tools and procedures required by the next construction stage from within its target root. Check mount exposure, writable paths, open descriptors and privilege controls so ordinary chroot execution cannot unintentionally alter host system paths. The readiness checks permit execution inside the temporary root during its construction, but do not end Bubblewrap host-write protection until **M2 has demonstrably rebuilt itself**. Once full M2 self-replication passes, subsequent ordinary controlled chroot execution requires no additional isolation layer. A failed readiness gate never authorizes unrestricted host execution.

**Temporary artifact and execution authority.** Cross-toolchain and temporary-tools outputs are standalone development artifacts, each recorded as a verified `tar.xz` archive of its resulting root filesystem with external digest/provenance. The M2 temporary-tools archive is the **sole source used to instantiate bootstrap chroots** for M3; do not assemble a bootstrap chroot by ad hoc file copying from independent intermediate roots. Injected build scripts execute as **root inside disposable chroots**, never against the host root. Generation A must possess and execute the tools and build procedures that construct its packages. The prototype's host-side Python runner, including any per-package injected Bash scripts, may help create generation A, but **may not be required to orchestrate or execute generation A's self-replication into generation B**. Package-specific build execution, sequencing, installation into the fresh target, and checks needed for replication must be driven using native capabilities available inside generation A. The foreign host may supply its kernel and controlled execution/mount interfaces, plus verified read-only source inputs, but not undeclared host executables, libraries, package-building logic, or Python-driven package dispatch.

**Self-replication proof.** Complete generation-A-to-generation-B reconstruction is the full M2 self-replication acceptance proof; do not require constructing generation C. Using generation A, construct a fresh and independently identifiable generation B from the verified source inputs and the declared M2 build instructions. Reproduce the **complete** required M2 toolchain, runtime, utilities, and native build procedures, not a representative subset; record component and dependency inventories for both generations. Confirm generation B operates its own compiler, linker, shell, build tools and supporting libraries in isolation, and contains the complete procedures and capabilities required for another equivalent replication (byte-identical binaries are not required). Inspect executable interpreters, search paths, dynamic libraries, installed files, and mount/input provenance for undeclared foreign-host userspace or copied-in bootstrap-only outputs.

**Failure and resumption.** Verify imported artifacts and source digests, detect incomplete extraction or installation, and never treat stamps or partially populated target roots as proof of completion. On resume, reuse consistent execution-local inputs and validated outputs or fail closed with explicit recovery instructions. Preserve independent generation-A and generation-B evidence, including package-specific commands/procedures actually run inside the native environment.

**Acceptance and M3 handoff.** M2 passes only when the full A-to-B self-replication completes from a fresh target, the reconstructed generation B is functionally complete and independent of foreign-host build tools or orchestration, and generation B retains the native procedures and tools needed to reproduce the same temporary environment; no generation-C execution is required. Retain machine-readable source, recipe, installed-closure, runtime-dependency, isolation, negative-contamination, failure, restart and cold-rebuild evidence. M3 consumes this self-hosting temporary environment to produce the first proper Distro package artifacts; M2 does not substitute its temporary installation state for Manage's eventual authoritative state.

### M3 — Bootstrap-chroot Distro packages

**Result and boundary.** M3 replaces temporary bootstrap construction with a definitive, managed Distro Build chroot whose complete required package closure can be rebuilt using Distro-native Build capabilities. The M2 temporary environment remains a construction input only, not an installed-package authority or source of untracked final files. M3 requires **one** fresh managed Build chroot and a full native rebuild of its own package closure; it does **not** require constructing a second Build chroot.

**Initial package production.** Materialize the disposable M3 bootstrap chroot solely by extracting the verified M2 temporary-tools `tar.xz` root artifact, then use that environment to build the first Distro-native toolchain, userspace, libraries and Build/Manage support packages. Build produces artifacts carrying the accepted `name + version + architecture + revision` identity and installable payload. Runtime relationships, ownership and whole-artifact checksums are produced for publication under the existing metadata and Package Database contracts; Manage does not consume Build recipes or temporary-root stamps as package authority. Resolve and record the complete package, runtime and build-dependency closure needed to reproduce the definitive Build chroot.

**Publication and integrity.** Establish the minimum Distro Build publication path, immutable artifact storage, coherent Package Database generation and repository interface needed by Manage. Publish referenced artifacts before making their metadata generation current. The generation includes the global requirement/version registry and applicable architecture catalog, and contains immutable artifact references, external whole-artifact checksums and authoritative runtime metadata. Reject incomplete, inconsistent or unverified publication and preserve prior valid generations.

**Managed Build-chroot construction.** Use Manage against a fresh empty target root to select the initial published collection, resolve its complete runtime dependencies and required providers, verify artifact identities and checksums, detect ownership and relationship conflicts, and install files and authoritative installed-package records. Record exact applied artifact checksums, package identities, install reasons, hold state and owned paths. Build owns build dependency intent and execution; Manage owns target-root package operations. Never copy the M2 root wholesale or import untracked bootstrap files. Specify safe failure and resumption behavior for partial application and installed-state commits.

**Complete native package reproduction.** Enter the managed Build chroot and use its Distro-native Build execution and orchestration to rebuild **every package necessary to constitute and operate that Build chroot**, including its compiler, assembler/linker, headers, runtime libraries, utilities, Build/Manage tools and required build-dependency closure. Define a finite, explicit authoritative inventory of that closure before testing, with evidence of every package's source, recipe, build dependencies, runtime dependencies and produced artifact. All package-specific build procedures execute using tools and dependencies available inside the managed environment, not Arch executables, host Python dispatch, M2 binaries or temporary construction-state shortcuts. Validate each rebuilt Distro package artifact against its expected identity, payload, metadata and integrity contracts. Newly rebuilt packages need not be installed into a second chroot or republished merely to pass M3; the initial collection must already have been published and used successfully by Manage.

**Acceptance and M4 handoff.** M3 passes only when Manage has assembled the definitive Build chroot from the initial published Distro packages and that chroot independently produces and validates the entire declared package closure required for its own operation. A representative package build alone is insufficient, but reconstructing a second Build chroot is unnecessary. Record the initial and rebuilt package inventories, published generation, source/recipe provenance, native build commands, artifact verification, installed-state integrity, runtime dependency closure, host-contamination checks and negative tests for checksum mismatch, dependency/ownership conflicts and interrupted operations. M4 consumes these proven Build, Manage and publication capabilities to construct a bootable package collection that retains native Build-chroot creation and package-building capability.

### M4 — Bootable package set

**Result and boundary.** M4 uses the proven M3 Distro-native Build chroot and Build/Manage/publication infrastructure to produce and publish the **complete bootable package manifest and all transitive runtime and build dependencies**. The set includes the Linux kernel, GRUB, systemd, essential userspace, and the Build/Manage tools and package access needed for later native Build-chroot creation. M4 is a native package-production and repository-completeness milestone; installation and independently booting the VM are M5 responsibilities. Do not substitute an already booted foreign-host system or copy bootstrap-only files into the collection.

**Manifest and dependency graph.** Start the native package-inventory prototype with the Linux kernel, GRUB, systemd and a minimal userspace (including Bash and coreutils), expanding the inventory to include each required build-time and runtime dependency as evidence demands; prototype the closure where necessary. Define one explicit, finite initial bootable manifest and recursively resolve its runtime and build dependency closure, including needed providers and the M3 seed packages. Distinguish package build dependencies from runtime dependencies and detect unresolved requirements and dependency cycles. Build in dependency order from the initial M3 published seed; bootstrap cycles require an explicit reviewed break or stage-specific procedure rather than silently accepting undeclared installed tools. Retain a stable per-execution selection of source identities, accepted recipes/build inputs and package identities across resumption, consistent with Build State and publication policy.

**Selected build-root strategy: isolated per package.** Every cache-miss package build runs in a **fresh, independently identified, disposable Distro Build root** provisioned by Manage from verified published Distro packages. Install the **entire published M3 package set as the native Build baseline** plus each package-specific declared build-dependency closure into that root; do not let artifacts or packages from a prior package build leak into it. Build owns dependency intent, source verification, build execution, staging and artifact creation; Manage owns dependency resolution, package application and installed state in each root. A verified read-only base image or copy-on-write snapshot may optimize root creation only if the effective installed inventory remains accounted for, isolated and equivalent to a fresh Manage-provisioned root. Do not default to one accumulating sequential chroot.

**Repository as checkpoint/cache.** The normal reuse operation is simply **Manage installing an already published, selected Distro package** from the repository, with its authoritative dependency resolution and artifact checksum verification. Do not introduce a separate build-cache identity or fingerprint protocol. Build State still controls whether a changed source, recipe or revision calls for a new build and publication; an installed or published artifact must not bypass those decisions. On a miss, validate the package and stage immutable artifact bytes first, then atomically publish a coherent Package Database generation referencing only available artifacts. The repository supplies subsequent dependency installations and durable checkpoints for interruption/resumption. A failed build must not publish an incomplete artifact or advance the current generation; a retry uses a clean per-package root and preserves already valid published artifacts.

**Complete-collection proof.** Continue until **every selected package and dependency in the bootable manifest closure** has a valid, available Distro artifact in one coherent published generation. Verify the installable runtime closure for the selected initial VM target, including GRUB/kernel/systemd and local userspace, and ensure the published collection makes the native Build and Manage capabilities and required Build-chroot packages available. Demonstrate dependency planning, per-package chroot separation, package verification, Manage-mediated published artifact reuse, interrupted-build resumption and negative tests for undeclared dependencies, missing providers, poisoned cache artifacts and interrupted publication. M4 does not require a second M3 Build-chroot self-rebuild or an installed VM boot; independent installed-VM boot and Distro-hosted M1→M2 self-replication are demonstrated in M5, without repeating M3/M4 package-build acceptance.

**Acceptance and M5 handoff.** M4 passes only when the M3 native Build environment has built or validly reused **the entire declared bootable manifest and recursive dependencies**, using isolated Manage-provisioned roots for every build performed, and published all resulting selected artifacts through coherent Distro repository state. Retain manifest closure, source and recipe decisions, build-root inventories, package identities, checksums, Manage installation/reuse decisions, publication generations, failure/restart evidence and VM-target compatibility inputs for Install in M5.

### M5 — Installed VM

**Result and boundary.** Install the M4 Distro package collection into a disposable VM and boot it independently through GRUB, Linux and systemd. From inside the running installed system, clone `wiigelec/distro` and execute the repository's **ordinary M1 → M2 bootstrap workflow with the installed Distro VM serving as the new foreign host**. M5 must freshly qualify this host, build and validate its own M1 cross-toolchain, build M2 from that handoff, and pass M2's complete A-to-B native self-replication proof. Do not bypass M1 because the Distro host already has a native compiler. The native package-production/managed Build-chroot proof belongs to M3 and M4; it is not an additional M5 acceptance gate.

**Installation and boot.** Select one explicit first VM target contract (virtual architecture, firmware, storage layout, filesystem and GRUB configuration). Install prepares the disposable target and configures the system, delegating all Distro package payload application and installed-package state to Manage. Verify published identities, checksums, dependencies, ownership and installed state. Boot the VM's installed kernel and systemd-managed usable local userspace independently of the original Arch host.

**Rebootstrap host prerequisites and protection.** M4's installed package set must provide Git, the selected repository transport and trust prerequisites, working networking where needed, native compiler/toolchain, build utilities, source-fetch and verification tools, and the filesystem/mount/execution facilities required to act as a bootstrap host. Clone `wiigelec/distro` from inside the VM into a fresh workspace and record the exact revision. Run the **normal bootstrap entry points**, using host qualification and source-selection adapters appropriate to Distro instead of Arch-only package-manager commands; these may differ by host, but the M1 construction and M2 acceptance contracts do not. As with the original bootstrap, use **Bubblewrap only**, with fail-closed bounded writable paths and read-only host system files, throughout M1 and M2 construction **until complete M2 generation-A-to-generation-B self-replication has passed**. A functional native chroot readiness check permits native execution inside the protected construction environment but does not end Bubblewrap protection early. After the complete M2 self-replication proof passes, use ordinary controlled native chroot execution without any mandatory additional namespace or container sandboxing. Chroot mounts, privileges, descriptors and writable paths must still be controlled to prevent host damage and untracked dependencies.

**Fresh M1 then M2.** In the newly cloned workspace, qualify the installed Distro VM as the host without modifying host packages, resolve and verify new execution-local upstream inputs, construct a fresh M1 assembler/linker, compiler, target headers and libc interface, and pass the full M1 toolchain, ELF and contamination checks. Construct M2 generation A from **that newly built M1 output**, with explicitly declared host assistance limited to initial construction. Then use A's native tools and build procedures to produce a distinct complete M2 generation B, validate its toolchain/runtime/utility/build-procedure closure, and show B can drive another equivalent replication. The newly constructed M1 and M2 may not reuse or copy outputs, temporary roots or workspace state from the original Arch-hosted bootstrap. Building only a sample program, invoking the scripts without a fresh result, or starting directly at M2 does not pass.

**M5 acceptance boundary.** The installed VM must boot successfully and function as the fresh foreign host for M1 and M2. Once its freshly constructed M2 completes full generation-A-to-generation-B self-replication, M5 is proven. M3/M4 separately establish the native managed Build-chroot and package-building capabilities; M5 need not repeat that separate package-building acceptance test.

**Failure, resumption and evidence.** Reject missing host capabilities, unverified source or clone identities, invalid package/installed state, boot failure, unsafe writable mounts, escaped host writes, target-toolchain contamination, incomplete M1/M2 outputs, or mismatched resume inputs. Recovery may reuse only individually validated outputs from the **current** Distro-hosted execution, never the earlier Arch-hosted bootstrap. Retain VM profile and boot evidence, installed package state, repository revision, host qualification, exact bootstrap commands, incrementally frozen source/version/digest identities, M1 and M2 root archive inventories, ELF/mount provenance, A-to-B proof and interrupted-run recovery. M5 passes once the independently booted installed VM acts as the host for a fresh M1 → M2 bootstrap and the new M2 root passes self-replication; no additional M5 managed-Build-chroot proof is required.

## Required cross-cutting engineering decisions at Planning review

The following decisions must be explicit before dependent Build work; avoid treating any prototype choice as already selected:

1. **Environment contract:** target architecture, host kernel/ABI constraints, bounded host-write protection before native chroot readiness, controlled chroot mounts/privileges afterward, and contamination-failure policy.
2. **Source trust:** source selection mapping, authenticity/checksum policy, exact per-execution locking, cache integrity, and resume behavior.
3. **Artifact format:** physical serialization of the established `name + version + architecture + revision` identity and installable payload, with checksum external to verified bytes.
4. **Package Database:** physical representation of atomic published generation, global requirement/version registry, architecture catalog, immutable artifact references, and artifact-before-metadata publication order.
5. **Bootstrap dependency closure:** native toolchain and runtime inventory needed for both Build chroot and M4 bootable set, with explicit relationships and ownership.
6. **Manage transaction substrate:** minimal correct target-root installation with checksum, path ownership, dependency checks and durable installed state; fail safely on partial application.
7. **VM/install target:** one specific first VM firmware/partition/filesystem configuration; general hardware support deferred, GRUB/systemd boot mandatory.
8. **Acceptance fixtures:** M2 complete temporary-environment A-to-B replication (without generation C), M3 complete managed Build-chroot package-closure reproduction, M4 complete bootable-manifest dependency-closure production/publication with fresh per-package builds and Manage package reuse, and M5 independently booted Distro-hosted M1 → M2 full self-replication.

The M4 build-root strategy is **selected**: fresh per-package Manage-provisioned roots and the published repository as the durable artifact checkpoint/cache. Host protection is selected as Bubblewrap only during M1 and M2 construction until full M2 self-replication succeeds; afterward controlled chroot execution requires no extra sandbox. Injected build scripts run as root within disposable chroots. Cross-toolchain and temporary-tools roots are standalone `tar.xz` development artifacts; M2 is the sole input used to create bootstrap chroots. Source identities are frozen incrementally per component. Initial native Build baseline is the M3 package set; ordinary artifact reuse is Manage installation, not a separate build cache. Exact commands and mount mechanics remain Planning details. Other decisions above remain open until explicitly resolved; no prototype defaults are implied. Resolve them in Planning before Build must rely on them; do not silently commit to Arch-derived recipe behavior, G1 database formats, tar layouts, or QEMU BIOS just because a prototype used them.

## Selected implementation decisions for FS-001 Planning

The following choices implement the accepted Design without changing its logical authorities. Only the first target and first VM profile are in scope; expand support by separate review.

- **Target/hosts (Q1–Q4):** initial `x86_64-distro-linux-gnu` target, Linux/glibc and GCC/Binutils; initial Arch host and later Distro-as-host. Qualify tools by executable behavior, introducing minimum host versions only for demonstrated incompatibilities. Arch detects host packages via `pacman`; Distro reads Manage-installed package state. Host adapters feed one common resolver.
- **Host safety/native execution (Q5–Q8):** Bubblewrap is the sole pre-bootstrap host-protection mechanism. Host system paths are read-only with explicitly bounded writable build directories. Injected package build scripts run as root **inside disposable chroots**, never against the host root. Use minimal controlled `/proc`, `/dev`, `/sys` mounts only as needed. Chroot readiness can be tested earlier, but compulsory Bubblewrap protection ends only when full M2 self-replication is proven; subsequently no additional isolation mechanism is required.
- **Source selection and trust (Q9–Q15):** qualify the **complete M1–M5 bootable bootstrap manifest and recursive build/runtime dependency closure before M1**, capturing installed host package identities, full distribution versions, upstream-version candidates, and evidence that corresponding upstream releases are resolvable. Reject missing or ambiguous equivalents without modifying host packages. The resulting host-version baseline is execution-local and fixed. On Arch use `pacman -Q` with epoch/pkgrel-aware parsing; on Distro use Manage installed state. Select, verify and lock source archive identities **incrementally at first consumption** from that fixed baseline. Verify upstream signatures when available against approved trusted fingerprints; otherwise accept official checksums obtained over authenticated HTTPS. Official upstream locations take precedence, with checksum-equivalent approved mirror fallbacks. Reject inconsistent bytes and allow offline resumption only for locked, verified inputs. Native recipes and Build State remain separate authorities.
- **Temporary development artifacts (Q16–Q18):** generation A producing an independently functional and complete generation B is sufficient evidence of M2 self-replication; no generation C is required. Cross-toolchain and temporary-tools outputs are independent `tar.xz` root-filesystem development artifacts with verified external checksums. The M2 archive alone materializes bootstrap construction chroots for M3. Compare complete inventories, ELF dependency closure and ability to build, not byte identity.
- **Package artifact interface (Q19–Q21):** use `tar.zst` for permanent Distro package artifacts, distinct from the temporary `tar.xz` development roots. Embed complete package identity with installable payload; keep authoritative dependency/conflict/provider/ownership metadata in Package Database. Preserve numeric UID/GID/mode payload semantics and define fixed system account identities as required. Whole-artifact checksums remain external.
- **Repository publication (Q22–Q25):** implement immutable versioned JSON Package Database generation snapshots, immutable checksum-addressed artifacts, and one atomic current-generation pointer. Serialize publication through one writer; permit separately built artifacts to await publication. Support local filesystem access and simple HTTP serving to the trusted network. Preserve Design's registry, current identity, highest published revision, and artifact-before-metadata semantics.
- **Manage installation (Q26–Q29):** use root-local SQLite installed-state representation and staged/transactional installation with explicit interrupted-operation recovery. Reject undeclared file ownership conflicts before modification; permit only model-authorized replacements. Package-local lifecycle behavior belongs to Manage; installation-wide machine configuration belongs to Install; general lifecycle hooks beyond bootstrap needs are deferred.
- **M3/M4 Build (Q30–Q34):** prototype an initial package inventory starting with Linux kernel, GRUB, systemd, Bash and coreutils; add all proven build-time and runtime dependencies. The complete M3 package collection is the baseline installed by Manage into each fresh M4 package build chroot. Resolve new package-specific dependencies as needed; bootstrap cycles require declared breaks. Reuse prototype discovery methods without making Debian authoritative. An already published package is reused by ordinary Manage installation; do not build a separate cache-fingerprint subsystem. Build State recipe acceptance/revision rules still govern when a new build is required.
- **Installed VM (Q35–Q39):** QEMU/KVM `x86_64`, BIOS GRUB on GPT with a BIOS boot partition and ext4 root; outbound user-mode VM networking for repository/source transport; native Git, CA, download/verification utilities, toolchain and Bubblewrap provisioned as Distro packages. Independently discover and incrementally lock Distro-host source versions. Once the installed VM has independently booted and its fresh M1-fed M2 has successfully self-replicated A→B, M5 acceptance is complete; no second clean VM or repeated M3 chroot package-build proof is required.
- **Implementation and validation (Q40–Q44):** Python/Bash scripting as appropriate for host orchestration, but Python is **not** a required bootstrap chroot or definitive Distro Build-chroot component and cannot be relied on for native A→B replication; host-side Python is permitted where the selected host provides it. Use the repository governance framework for validation, with stage-appropriate success/failure and integrity checks. Fail closed and retain verified checkpoints; implement sequential package construction initially. Initial full execution uses Arch and QEMU/KVM with reproducible evidence.

Physical serialization and transaction particulars not specified above (e.g., tar identity-entry schema, JSON layout and SQLite tables) remain to be documented as implementation detail without changing these selections or accepted Design semantics.

## Prototype-evidence decisions for FS-001

The eight `proto/*` branches provide non-normative construction evidence, not Design authority, accepted package state, or completed FS-001 acceptance. The decisions below refine implementation intent while preserving the five milestones, current normative requirements and their inactive state. Where a prototype conflicts with accepted Design or this Plan, the accepted contracts control.

### PE-1 — M1 construction sequence

Select the investigated progression of target Binutils, bootstrap GCC, Linux API headers, glibc, and compiler/C++ runtime finalization as the initial M1 construction baseline. Keep the `x86_64-distro-linux-gnu` toolchain-prefix and sysroot roles distinct. Qualify compiler target and search paths, ELF interpreter and library dependencies, and C/C++ compile/link/execute behavior before exporting the independently checked M1 root. `proto/distro-bootstrap-chroot` and `proto/bootstrap-staging` provide example procedures and failure cases, not approved source versions or a complete host equivalence policy. Resolve and lock verified source identities incrementally as EC-1 requires; neither prototype hardcoded versions nor completion stamps are source authority.

### PE-2 — Native execution and staged-result equivalence

Select the investigated `proto/lfs-optimize` pattern of disposable native construction roots, explicit build/test/install phases, staged payload capture, and verification that an artifact-realized filesystem matches the intended direct-install result. Check file types and bytes, numeric UID/GID, modes, symlink and hardlink semantics, and intended deletions; reject unsupported filesystem transitions. Declare temporary mounts and keep them outside payloads. M2 generation A must itself supply and execute the complete native build procedures and orchestration to reconstruct B; host Python package dispatch from the prototype is not admissible. In M3/M4 replace the prototype's `tar.xz` cache and direct-extraction reuse path with identity-bearing `tar.zst`, external SHA-256, published Package Database metadata and Manage-provisioned package roots. Do not introduce a second cache-fingerprint authority.

### PE-3 — Dependency-closure discovery fixtures

Seed candidate package inventories from `proto/lfs-optimize/package-set.json` (its 80-package normal LFS proof), `proto/g1-bootable` and its build-tools list. These are not accepted Distro manifests or source/version selections. Distinguish M2 self-replicating temporary tools and procedures, M3 definitive Build-chroot runtime/build closure, M4 complete bootable collection with ongoing native Build/Manage capability, and M5 fresh Distro-hosted bootstrap prerequisites. For each selected component, record host/upstream mapping, source verification, build/runtime edges, provider resolution, order, and explicitly reviewed cycle breaks. Freeze a finite authoritative inventory before the relevant complete-closure milestone proof. Discovery may expand it, but cannot silently weaken acceptance. Continue to apply EC-1 qualification instead of importing pinned LFS versions.

### PE-4 — Artifact application and filesystem integrity

Use `proto/lfs-optimize/artifact.py` snapshot/equivalence checks and `proto/g1-chroot/manage.py` artifact identity, checksum, archive-member and path-conflict preflight as candidate mechanisms and negative-test fixtures. Before target mutation, verify selected whole-artifact checksum, embedded canonical identity, target-root-relative paths and link containment, ownership and all dependency/conflict constraints. After application verify applied-file fidelity and installed-state consistency. The permanent interchange and authority remain those in EC-3 and EC-4. These prototype checks do **not** establish crash-consistent SQLite/filesystem transaction semantics. Before dependent Build work, settle externally observable identity encoding, shared directory and mutable configuration semantics. Interrupted-operation detection and safe recovery are required; full rollback after filesystem mutation is not an accepted Design guarantee.

### PE-5 — Initial VM installation implementation

Use `proto/g2-installer` as a candidate Install-to-Manage orchestration: confirm a disposable target block device, partition and format it, delegate every package payload and installed-state change to Manage, write filesystem/boot configuration, and install GRUB. Retain destructive-operation confirmation, controlled mounts and failure cleanup. Adapt the prototype's MBR layout to FS-001's selected BIOS-GRUB-on-GPT configuration with a BIOS boot partition and ext4 root. Use boot/systemd runtime evidence approaches from `proto/lfs-optimize`. Neither prototype replaces M5's independent VM boot followed by a fresh Distro-hosted M1 and complete M2 A-to-B replication.

### Still unresolved: explicit Planning and proof obligations

- **Host/source mapping (Planning):** The observed executable and `pacman` probes plus builder-discovery capability evidence do not resolve all host-to-upstream equivalences. Specify treatment of split packages, virtual capabilities, absent counterparts, and Distro-host mappings; if strict installed-host equivalence itself must change, return that semantic question to Design.
- **M2 A-to-B independence (Build proof after Plan resolution):** Neither investigated prototype proves a complete A-to-B native reconstruction under the current acceptance contract. Retain independent inventories, procedures, ELF/host contamination checks, negative and restart evidence. Any consequential unselected construction contract returns to Planning before Build proceeds.
- **Manage interrupted-operation recovery (Build contract and proof):** No prototype proves SQLite-plus-filesystem crash safety. Build must implement durable detection of interrupted target-root operations, prevent partial results from being reported as committed, and fail closed when safe automatic recovery is unavailable. Journal encoding, staging/mutation order, repair algorithm, and guarantees beyond the selected FS-001 boundary are implementation work; automatic rollback after partial filesystem mutation remains undecided in Manage Design.

These evidence selections do not activate normative requirements, create validation task bindings, change Design meaning, or establish a new acceptance or cache authority.

## Execution contracts for Build handoff

These contracts define the minimum interfaces and stage gates needed to realize the selected Planning decisions. Physical schemas, command names and precise package lists may be implemented in Build, but may not weaken the accepted Design, source-verification decisions or milestone acceptance. The FS remains in Planning; all normative requirements remain Inactive until separately activated through governance.

### EC-1 — Qualified-host source resolution

- **Mandatory whole-manifest preflight before M1:** determine the complete initial bootable bootstrap package manifest covering M1–M5 and its recursive build/runtime dependencies *before* cross-toolchain construction. Every selected component must have a traceable installed-host package/version basis and a resolvable corresponding upstream source release; check them all in a single qualification gate. Arch reads installed package identity/version through `pacman -Q`; Distro reads Manage installed-package state. Capture the full host version (`epoch:pkgver-pkgrel` where applicable), derive the upstream version candidate by stripping the optional epoch and final Arch package release, and explicitly resolve exceptions such as source/output split packages, aliases and version rewrites. Do not infer that parsed `pkgver` proves upstream source identity. Missing, ambiguous or unavailable upstream mappings fail the preflight and require explicit user remedy or mapping review; bootstrap never installs, upgrades or removes host packages. No M1 build starts until the entire required baseline is qualified.
- Keep three identities distinct: host package name/version, upstream source release, and eventual Distro package identity. Normalize host epoch/release/packaging suffixes with a recorded package-specific mapping where needed; do not assume normalized equality establishes source authenticity. Ambiguous mappings require review and cannot be resolved by lexical guesswork.
- **Separate host qualification from artifact locking:** freeze the complete qualified host package/version and upstream-release mapping baseline before M1. At each component's first source consumption, authenticate/verify its source and atomically persist an execution-local source lock: qualified host evidence, upstream name/version, URLs, verification method and trusted key when relevant, digest, recipe/input identity and selection order. Resume checks the fixed baseline, existing locks and cached bytes; it must not re-resolve changed host versions. If Build discovers a required component absent from the preflight closure, do not extend the baseline silently: stop, update and review the manifest, and run a new full preflight as a new execution. The source lock does not become the Package Manifest or Build State.
- For source trust, prefer upstream signatures checked against preapproved key fingerprints; if no signature exists, require an official checksum retrieved through authenticated HTTPS. A fallback mirror is permissible only with independently locked verified identity. Offline resume is allowed when locked verified bytes are present. Reject discrepancies, missing host prerequisite versions and unknown signing keys with diagnosable failures.

### EC-2 — Standalone M1/M2 root handoffs and protected execution

- M1 exports a complete standalone `tar.xz` archive of the cross-toolchain root with an **external** SHA-256 digest and an inventory of executables, links, libraries, target triple, loader/search-path probes and declared foreign-host allowances. M2 must validate the handoff before using it; an archive path or completion stamp alone is insufficient.
- M2 generation A uses M1 output to reconstruct a **fresh** generation B with native tools and native build procedures, no host-Python package dispatcher. Success requires the **complete** temporary toolchain, utilities, runtime and procedure closure in B, plus functional/ELF/dependency verification. Generation C is **not** required. Export the accepted M2 root as an independently verified `tar.xz` archive and retain A/B inventories and exact reproduction commands.
- The verified M2 root archive is the **sole root-filesystem construction source** for a disposable M3 bootstrap chroot. The exact generation chosen for archiving must be the validated self-replicated native result (B), not a mixture of A, M1 and host files. Verify archive checksum before extraction; reject absolute/traversal paths and unsafe links/devices; extract into a fresh designated target without writing outside it. Workspaces, sources, logs and execution locks remain external inputs/state rather than hidden installed root contents.
- During M1 and through completed M2 A→B proof, Bubblewrap is the **only** host filesystem protection arrangement: host paths read-only, named writable roots only, failed setup fails closed. Native chroot readiness checks do **not** end that protection. After M2 acceptance, controlled chroots may run without an additional container layer, with intentional mounts, bounded writable paths and closed inherited descriptors. Injected build scripts execute as root inside disposable roots; this grants no authority to change host system paths.

### EC-3 — Distro package artifact and metadata boundary

- Permanent packages are `tar.zst` artifacts distinct from temporary root archives. Each artifact contains a reserved, schema-versioned canonical identity entry (`name`, opaque `version`, `architecture`, `revision`) and an installable filesystem payload. The checksum is SHA-256 over the **whole compressed artifact** and resides in authoritative external published metadata; it is not a fifth identity field. Exact reserved entry path and canonical encoding must be fixed consistently by Build and Manage before either relies on interchange.
- Only the Package Database generation is authority for repository-backed `depends`, `conflicts`, `provides` and `owned_paths`. Do **not** duplicate those runtime relationships into an artifact as a competing metadata copy. Manage validates the whole-artifact digest and embedded identity against the selected published identity before payload application. Installed paths must normalize as target-root-relative, reject traversal and conflicts, and preserve numeric UID/GID and modes under the selected target policy. Directory/shared-path and mutable-configuration decisions that affect a selected package must be specified before publishing it.
- Build records the accepted recipe SHA and revision in **Build State**, not Manage's installed database. Initial upstream versions start at `r1`; a recipe-SHA change triggers required review, and published runtime metadata changes require a new revision. Manage never consults recipes to install a package.

### EC-4 — Published generation, Manage target state and interrupted changes

- Initial Package Database serialization is a versioned immutable **JSON generation snapshot** containing a global persistent `requirements` registry (`kind` plus ordered `versions`) and architecture catalogs with available highest-revision identities, explicit `current`, immutable artifact references, external checksums and authoritative runtime metadata. Every catalog in the generation observes one identical global registry. Names/kinds and previously established version ordering are permanent anchors. This is distinct from the maintainer Package Manifest and machine-maintained Build State.
- Publication is single-writer. Stage and verify new immutable checksum-addressed artifacts first, construct and validate a complete new generation, durably persist it, and **atomically switch one current-generation pointer last**. Failures before the switch leave the former generation current. Readers pin one generation; retain its referenced artifacts. Local filesystem access is supported, with HTTP transport exposing the same immutable generation/artifact semantics for the initial trusted-network environment.
- Manage's authoritative per-target installed state is a **root-local SQLite database** projecting package identity, applied artifact checksum, runtime relationships, ownership, explicit/dependency install reason and hold state. Before any payload mutation, resolve dependency/provider/hold/ownership checks and verify all chosen immutable artifacts. Apply a transaction under a target-root lock using recoverable staging/journaling; do not equate an SQLite commit with atomic filesystem payload changes. Before reporting a successful transaction, verify that its installed-state records and affected filesystem payload agree. After interruption, detect and record unfinished work; on restart, either demonstrate a safe, consistent completed or restored state, or block further package mutations with an actionable recovery report. Never report a partial installation as successful, and never silently overwrite ambiguous state. This initial FS-001 rule does not require automatic rollback of every partial filesystem mutation, which Manage Design leaves undecided. Build selects the journaling, staging, repair mechanics and interruption test fixtures.
- Install prepares disks, partitions, boot setup and machine configuration; it invokes Manage for every package application and installed-state change. Build creates artifacts; it does not mutate Manage's installed target state. The physical schema and staging mechanism are Build-phase implementation choices, but the transaction and authority boundaries are fixed here.

### EC-5 — Dependency closure and initial package production

- Prototype the initial bootable goals starting with Linux kernel, GRUB, systemd, Bash and coreutils, then **discover** and document every required dependency rather than assuming those five packages constitute a complete bootable system. Host-installed-version qualification remains mandatory for every new package admitted to the M1–M5 selection. Record both build and runtime edges, providers, order and reviewed bootstrap cycle breaks.
- M3 uses the verified M2 artifact to produce and publish the initial native Distro package collection; Manage assembles exactly **one fresh definitive Build chroot** from these packages. Build inside it must reproduce the **entire recorded M3 package closure**, including its build/runtime/toolchain dependencies. No second definitive chroot or generation C is required.
- M4 installs the **complete published M3 set** as the baseline into a new Manage-provisioned disposable Build root for each newly built package, plus its declared package-specific build dependencies. Build executes the script as root in that disposable root; packages from previous builds never leak in. The repository is the durable checkpoint: reuse is **ordinary Manage installation** of a selected, verified published package, not an independent build-cache fingerprint system. Build State still determines when source/recipe/revision changes require a new artifact.
- Before M4 passes, one coherent published generation must contain the entire transitive bootable runtime/build closure and all host-side bootstrap prerequisites that the installed VM needs to act as a Distro host for M1→M2. A component absent from the installed VM is not silently supplied by the Arch host.

### EC-6 — Governance evidence and milestone exit criteria

- Register stage-appropriate validation and review evidence **through existing repository governance** when requirements are activated in Build; do not create an alternative validation runner or claim inactive requirements have mechanical bindings. At Planning, the acceptance contract names proof obligations, not unimplemented test IDs.
- M1: verified host and incremental source-resolution evidence, complete M1 root archive, target compile/link/runtime checks and contamination rejection.
- M2: independent native A→B rebuild of the complete required root closure, verified B archive/inventory and absence of undeclared host userspace/orchestration, with interrupted/restart and negative evidence; **no C build**.
- M3: initial published native package set, one Manage-assembled definitive Build chroot, full native rebuilding of that chroot's authoritative package closure and artifact/metadata/ownership integrity evidence.
- M4: full selected bootable dependency closure published coherently, fresh per-package Manage roots, install/reuse of published packages and failure/resume tests. No second M3 package-closure rebuild or VM boot proof at M4.
- M5: boot the installed VM through GRUB/Linux/systemd, clone the repository there, freshly qualify Distro and build independent M1→M2; **complete A→B self-replication is the final M5 proof**. Do not add another installed-VM managed Build-chroot test or second complete clean VM run.

## Evidence and validation strategy

- For M1–M2, retain machine-readable input, source checksum, **standalone cross-toolchain and M2 `tar.xz` root-artifact digests/inventories**, environment, stage, runtime linkage, host protection, and failure evidence.
- For M3–M4, retain published package identities and integrity, database generation, Manage-installed closure and file inventory, and successful independent builds.
- For M5, retain installer commands, selected VM target, installed package state, GRUB/systemd boot marker, cloned repository revision, Distro-as-host qualification, fresh M1 and M2 artifact/replication evidence. Its acceptance ends after full M2 self-replication inside the booted VM.
- Include negative checks for host contamination, modified source/artifact checksums, incomplete generation publication, ownership conflicts, invalid dependency closure, and inability to form an independent Build chroot.
- Bind each active mechanical requirement to concrete registered product Validation tasks during Build. A successful mechanical run does not replace semantic review.

`proto/distro-bootstrap-chroot` informs host qualification and staged toolchain work; `proto/lfs-optimize` informs native construction and validation; `proto/g1-chroot`, `proto/g1-bootable`, and `proto/g2-installer` inform package, boot and install proofs; `proto/builder-discovery` and `proto/maint-lifecycle` inform source/recipe discovery and correction; `proto/bootstrap-staging` informs early staging methods. Reuse compatible mechanisms selectively without inheriting superseded semantics.
