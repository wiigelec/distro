# FS-001 — Bootstrap Plan

## Intent and governing boundaries

This Plan realizes `functional-set.md` at Design revision `12e71d53fde329b16b14ed8103136443696efa70`. Build, Manage, and Install remain distinct authorities. Bootstrap construction roots are temporary and must not become an alternative permanent package format or package-management authority. A definitive Build chroot is created by Manage from Distro-produced packages, not by copying the temporary chroot. M4 must supply the capability to create that Build chroot and produce native packages; M5 must demonstrate those capabilities *from the installed VM*.

## Technical realization by milestone

### M1 — Cross-toolchain

**Result and boundary.** M1 produces a validated Distro-targeting cross-toolchain, target headers and C runtime interface sufficient for M2. It is not the definitive Distro Build chroot or an installed system. Its construction may use explicitly declared Arch host tools, but exported target components must be distinguished from host inputs.

**Host qualification.** On the initial Arch Linux host, record architecture and kernel information, required build utilities and their executable versions, compiler/linker capability, and potentially contaminating build environment settings. Qualification shall separately establish (1) tool availability and working C/C++ compile/link probes, (2) compatibility with the chosen target interfaces, (3) the ability to execute the chosen isolation arrangement including mount and permission behavior, and (4) availability and verification of resolved upstream sources. Fail with actionable deficiencies; never install, upgrade or remove host packages. Minimum host/kernel versions shall be justified by observed compatibility results, not assumed from package presence or prototype constants. The same qualification and construction workflow must also be executable on the installed Distro VM acting as a new bootstrap host in M5. Keep host-package version detection and other distribution-specific probes behind explicit host adapters; neither the M1 build logic nor source resolution may require `pacman` when running on Distro.

**Source selection and restart identity.** Start each *new* bootstrap execution by qualifying the current host (initially Arch, then Distro for M5) and mapping the host’s installed required bootstrap-tool package versions to corresponding upstream source releases. Resolve host-specific package names and version formats through explicit adapters, normalizing distribution release suffixes and other differences without requiring Arch-specific tooling on Distro. Record selected source identity, exact version, source URL, verification method, verified digest and any signature evidence in execution-local state. Once selection for that execution is established, subsequent steps and resumption must reuse those exact verified inputs and reject changed or inconsistent cached bytes; restarting with new host-derived selections is a **new** execution. No repository-maintained bootstrap-version catalog or enduring upstream-tracking policy is created.

**Host-write protection and target contract.** Select one initial target architecture, target triple, Linux ABI and GNU C library strategy as a *Planning* contract before dependent toolchain construction. The prototype's `x86_64-distro-linux-gnu` is evidence, not yet an accepted selection. Before the native bootstrap chroot is functional, use Bubblewrap or an equivalent bounded arrangement primarily to protect the host filesystem against accidental writes: host system paths are read-only and only named workspaces and target roots are writable. Specify allowed host tools/libraries, mounts, environment, UID and privilege behavior, and cleanup. Do not silently fall back to elevated or unrestricted execution if those protections cannot be established. Inspect actual host-versus-target dependencies separately; host-write protection alone does not establish native independence.

**Construction.** Build the target assembler/linker, initial compiler, Linux API headers, C library interface, and necessary compiler/runtime finalization in an explicit dependency order. Keep the toolchain installation root and target sysroot distinguishable; declare each intermediate host dependency and each input carried forward to M2. The cross-toolchain need not be made into a final Distro package in M1.

**Acceptance and M2 handoff.** Require fresh-workspace construction and inspect compiler driver configuration, target triple, search paths, generated ELF interpreters and dynamic-library closure. Run representative target C and C++ compile/link/execute probes in a suitable isolated target context, including a negative contamination case. Verify that observed dependencies match the declared intermediate foreign-host allowances and that M2 will use the intended target headers, linker and libc, rather than silently taking them from the Arch host. Record machine-readable qualification, selected source identities/digests, build input and environment, toolchain output inventory, probes, failures, and restart evidence. M2 begins only after these checks pass.

### M2 — Temporary tools

**Result and boundary.** M2 delivers a temporary, Distro-native-capable build environment that can **reproduce its entire required temporary toolchain and userspace closure**. It is not the definitive managed Build chroot or an installed Distro system. M2's first generation may use the validated M1 cross-toolchain and explicitly declared foreign-host assistance; M2 acceptance is based on native self-replication, not on the ability to execute a shell or compile one sample program.

**First-generation construction.** Import the verified M1 handoff and construct generation A in a distinct temporary root, keeping installed files separate from sources, workspaces, scripts, logs and completion records. Select the complete native shell, compiler, assembler/linker, build utilities, headers, libraries, and other capabilities needed to reproduce the M2 environment and support M3. Derive source identities from the current bootstrap execution's verified inputs rather than hardcoded prototype version pins. Declare all foreign-host tools and permitted intermediate construction dependencies.

**Native chroot readiness and transition.** Before ceasing the pre-chroot host-write protection, verify that generation A can execute its native shell, dynamic loader and shared-library closure, essential filesystem utilities, and the tools and procedures required by the next construction stage from within its target root. Check mount exposure, writable paths, open descriptors and privilege controls so ordinary chroot execution cannot unintentionally alter host system paths. On a passing readiness gate, normal controlled chroot execution suffices without mandatory additional namespace or container sandboxing. A failed readiness gate never authorizes unrestricted host execution.

**Native execution authority.** Generation A must possess and execute the tools and build procedures that construct its packages. The prototype's host-side Python runner, including any per-package injected Bash scripts, may help create generation A, but **may not be required to orchestrate or execute generation A's self-replication into generation B**. Package-specific build execution, sequencing, installation into the fresh target, and checks needed for replication must be driven using native capabilities available inside generation A. The foreign host may supply its kernel and controlled execution/mount interfaces, plus verified read-only source inputs, but not undeclared host executables, libraries, package-building logic, or Python-driven package dispatch.

**Self-replication proof.** Using generation A, construct a fresh and independently identifiable generation B from the verified source inputs and the declared M2 build instructions. Reproduce the **complete** required M2 toolchain, runtime, utilities, and native build procedures, not a representative subset; record component and dependency inventories for both generations. Confirm generation B operates its own compiler, linker, shell, build tools and supporting libraries in isolation, and can itself execute the same replication procedure (a repeatability proof; byte-identical binaries are not required). Inspect executable interpreters, search paths, dynamic libraries, installed files, and mount/input provenance for undeclared foreign-host userspace or copied-in bootstrap-only outputs.

**Failure and resumption.** Verify imported artifacts and source digests, detect incomplete extraction or installation, and never treat stamps or partially populated target roots as proof of completion. On resume, reuse consistent execution-local inputs and validated outputs or fail closed with explicit recovery instructions. Preserve independent generation-A and generation-B evidence, including package-specific commands/procedures actually run inside the native environment.

**Acceptance and M3 handoff.** M2 passes only when the full A-to-B self-replication completes from a fresh target, the reconstructed generation B is functionally complete and independent of foreign-host build tools or orchestration, and generation B can drive another equivalent replication. Retain machine-readable source, recipe, installed-closure, runtime-dependency, isolation, negative-contamination, failure, restart and cold-rebuild evidence. M3 consumes this self-hosting temporary environment to produce the first proper Distro package artifacts; M2 does not substitute its temporary installation state for Manage's eventual authoritative state.

### M3 — Bootstrap-chroot Distro packages

**Result and boundary.** M3 replaces temporary bootstrap construction with a definitive, managed Distro Build chroot whose complete required package closure can be rebuilt using Distro-native Build capabilities. The M2 temporary environment remains a construction input only, not an installed-package authority or source of untracked final files. M3 requires **one** fresh managed Build chroot and a full native rebuild of its own package closure; it does **not** require constructing a second Build chroot.

**Initial package production.** Use the validated, self-replicating M2 environment to build the first Distro-native toolchain, userspace, libraries and Build/Manage support packages. Build produces artifacts carrying the accepted `name + version + architecture + revision` identity and installable payload. Runtime relationships, ownership and whole-artifact checksums are produced for publication under the existing metadata and Package Database contracts; Manage does not consume Build recipes or temporary-root stamps as package authority. Resolve and record the complete package, runtime and build-dependency closure needed to reproduce the definitive Build chroot.

**Publication and integrity.** Establish the minimum Distro Build publication path, immutable artifact storage, coherent Package Database generation and repository interface needed by Manage. Publish referenced artifacts before making their metadata generation current. The generation includes the global requirement/version registry and applicable architecture catalog, and contains immutable artifact references, external whole-artifact checksums and authoritative runtime metadata. Reject incomplete, inconsistent or unverified publication and preserve prior valid generations.

**Managed Build-chroot construction.** Use Manage against a fresh empty target root to select the initial published collection, resolve its complete runtime dependencies and required providers, verify artifact identities and checksums, detect ownership and relationship conflicts, and install files and authoritative installed-package records. Record exact applied artifact checksums, package identities, install reasons, hold state and owned paths. Build owns build dependency intent and execution; Manage owns target-root package operations. Never copy the M2 root wholesale or import untracked bootstrap files. Specify safe failure and resumption behavior for partial application and installed-state commits.

**Complete native package reproduction.** Enter the managed Build chroot and use its Distro-native Build execution and orchestration to rebuild **every package necessary to constitute and operate that Build chroot**, including its compiler, assembler/linker, headers, runtime libraries, utilities, Build/Manage tools and required build-dependency closure. Define a finite, explicit authoritative inventory of that closure before testing, with evidence of every package's source, recipe, build dependencies, runtime dependencies and produced artifact. All package-specific build procedures execute using tools and dependencies available inside the managed environment, not Arch executables, host Python dispatch, M2 binaries or temporary construction-state shortcuts. Validate each rebuilt Distro package artifact against its expected identity, payload, metadata and integrity contracts. Newly rebuilt packages need not be installed into a second chroot or republished merely to pass M3; the initial collection must already have been published and used successfully by Manage.

**Acceptance and M4 handoff.** M3 passes only when Manage has assembled the definitive Build chroot from the initial published Distro packages and that chroot independently produces and validates the entire declared package closure required for its own operation. A representative package build alone is insufficient, but reconstructing a second Build chroot is unnecessary. Record the initial and rebuilt package inventories, published generation, source/recipe provenance, native build commands, artifact verification, installed-state integrity, runtime dependency closure, host-contamination checks and negative tests for checksum mismatch, dependency/ownership conflicts and interrupted operations. M4 consumes these proven Build, Manage and publication capabilities to construct a bootable package collection that retains native Build-chroot creation and package-building capability.

### M4 — Bootable package set

**Result and boundary.** M4 uses the proven M3 Distro-native Build chroot and Build/Manage/publication infrastructure to produce and publish the **complete bootable package manifest and all transitive runtime and build dependencies**. The set includes the Linux kernel, GRUB, systemd, essential userspace, and the Build/Manage tools and package access needed for later native Build-chroot creation. M4 is a native package-production and repository-completeness milestone; installation and independently booting the VM are M5 responsibilities. Do not substitute an already booted foreign-host system or copy bootstrap-only files into the collection.

**Manifest and dependency graph.** Define one explicit, finite initial bootable manifest and recursively resolve its runtime and build dependency closure, including needed providers and the M3 seed packages. Distinguish package build dependencies from runtime dependencies and detect unresolved requirements and dependency cycles. Build in dependency order from the initial M3 published seed; bootstrap cycles require an explicit reviewed break or stage-specific procedure rather than silently accepting undeclared installed tools. Retain a stable per-execution selection of source identities, accepted recipes/build inputs and package identities across resumption, consistent with Build State and publication policy.

**Selected build-root strategy: isolated per package.** Every cache-miss package build runs in a **fresh, independently identified, disposable Distro Build root** provisioned by Manage from verified published Distro packages. Install the declared package build-dependency closure (and a documented baseline toolchain) into that root; do not let artifacts or packages from a prior package build leak into it. Build owns dependency intent, source verification, build execution, staging and artifact creation; Manage owns dependency resolution, package application and installed state in each root. A verified read-only base image or copy-on-write snapshot may optimize root creation only if the effective installed inventory remains accounted for, isolated and equivalent to a fresh Manage-provisioned root. Do not default to one accumulating sequential chroot.

**Repository as checkpoint/cache.** Before building a package, consult the authoritative published Package Database generation and Build State for a reusable artifact. A cache hit requires a matching selected published package identity, verified artifact checksum and evidence that the accepted source, recipe, revision and relevant build inputs remain applicable; package name alone is insufficient. On a miss, validate the package and stage immutable artifact bytes first, then atomically publish a coherent Package Database generation referencing only available artifacts. The repository supplies subsequent dependency installations and durable checkpoints for interruption/resumption. A failed build must not publish an incomplete artifact or advance the current generation; a retry uses a clean per-package root and preserves already valid published artifacts.

**Complete-collection proof.** Continue until **every selected package and dependency in the bootable manifest closure** has a valid, available Distro artifact in one coherent published generation. Verify the installable runtime closure for the selected initial VM target, including GRUB/kernel/systemd and local userspace, and ensure the published collection makes the native Build and Manage capabilities and required Build-chroot packages available. Demonstrate dependency planning, per-package isolation, package verification, source/recipe-aware cache reuse, interrupted-build resumption and negative tests for undeclared dependencies, missing providers, poisoned cache artifacts and interrupted publication. M4 does not require a second M3 Build-chroot self-rebuild or an installed VM boot; M5 demonstrates post-install Build-chroot creation and package building from the VM.

**Acceptance and M5 handoff.** M4 passes only when the M3 native Build environment has built or validly reused **the entire declared bootable manifest and recursive dependencies**, using isolated Manage-provisioned roots for every build performed, and published all resulting selected artifacts through coherent Distro repository state. Retain manifest closure, source and recipe decisions, build-root inventories, package identities, checksums, cache-hit decisions, publication generations, failure/restart evidence and VM-target compatibility inputs for Install in M5.

### M5 — Installed VM

**Result and boundary.** Install the M4 Distro package collection into a disposable VM and boot it independently through GRUB, Linux and systemd. From inside the running installed system, clone `wiigelec/distro` and execute the repository's **ordinary M1 → M2 bootstrap workflow with the installed Distro VM serving as the new foreign host**. M5 must freshly qualify this host, build and validate its own M1 cross-toolchain, build M2 from that handoff, and pass M2's complete A-to-B native self-replication proof. Do not bypass M1 because the Distro host already has a native compiler. Preserve the separate installed-VM proof of definitive managed Build-chroot construction and representative package building.

**Installation and boot.** Select one explicit first VM target contract (virtual architecture, firmware, storage layout, filesystem and GRUB configuration). Install prepares the disposable target and configures the system, delegating all Distro package payload application and installed-package state to Manage. Verify published identities, checksums, dependencies, ownership and installed state. Boot the VM's installed kernel and systemd-managed usable local userspace independently of the original Arch host.

**Rebootstrap host prerequisites and protection.** M4's installed package set must provide Git, the selected repository transport and trust prerequisites, working networking where needed, native compiler/toolchain, build utilities, source-fetch and verification tools, and the filesystem/mount/execution facilities required to act as a bootstrap host. Clone `wiigelec/distro` from inside the VM into a fresh workspace and record the exact revision. Run the **normal bootstrap entry points**, using host qualification and source-selection adapters appropriate to Distro instead of Arch-only package-manager commands; these may differ by host, but the M1 construction and M2 acceptance contracts do not. As with the original bootstrap, protect the new host's system files against accidental writes using an explicitly bounded, fail-closed writable-filesystem arrangement (Bubblewrap or equivalent) during M1 and pre-chroot M2 construction. Once the new temporary chroot passes its functional readiness gate, use native chroot execution; do not require additional namespace/container sandboxing solely for later native builds. Chroot mounts, privileges, descriptors and writable paths must still be controlled to prevent host damage and untracked dependencies.

**Fresh M1 then M2.** In the newly cloned workspace, qualify the installed Distro VM as the host without modifying host packages, resolve and verify new execution-local upstream inputs, construct a fresh M1 assembler/linker, compiler, target headers and libc interface, and pass the full M1 toolchain, ELF and contamination checks. Construct M2 generation A from **that newly built M1 output**, with explicitly declared host assistance limited to initial construction. Then use A's native tools and build procedures to produce a distinct complete M2 generation B, validate its toolchain/runtime/utility/build-procedure closure, and show B can drive another equivalent replication. The newly constructed M1 and M2 may not reuse or copy outputs, temporary roots or workspace state from the original Arch-hosted bootstrap. Building only a sample program, invoking the scripts without a fresh result, or starting directly at M2 does not pass.

**Managed Build-chroot proof.** Independently of the fresh M1 → M2 bootstrap test, use Manage and M4-published Distro packages **inside the booted VM** to assemble a new definitive Build chroot. Use native Build there to produce and validate a representative Distro package. This confirms the installed package-management path and does not replace M1 → M2 acceptance.

**Failure, resumption and evidence.** Reject missing host capabilities, unverified source or clone identities, invalid package/installed state, boot failure, unsafe writable mounts, escaped host writes, target-toolchain contamination, incomplete M1/M2 outputs, or mismatched resume inputs. Recovery may reuse only individually validated outputs from the **current** Distro-hosted execution, never the earlier Arch-hosted bootstrap. Retain VM profile and boot evidence, installed package state, repository revision, host qualification, exact bootstrap commands, source/version/digest lock, M1 and M2 build inventories, ELF/mount provenance, A-to-B proof, interrupted-run recovery and the separate managed Build-chroot artifact. M5 passes only when the installed VM can act as the foreign host for its own fresh M1 → M2 bootstrap and separately build a package from a new managed Build chroot.

## Required cross-cutting engineering decisions at Planning review

The following decisions must be explicit before dependent Build work; avoid treating any prototype choice as already selected:

1. **Environment contract:** target architecture, host kernel/ABI constraints, bounded host-write protection before native chroot readiness, controlled chroot mounts/privileges afterward, and contamination-failure policy.
2. **Source trust:** source selection mapping, authenticity/checksum policy, exact per-execution locking, cache integrity, and resume behavior.
3. **Artifact format:** physical serialization of the established `name + version + architecture + revision` identity and installable payload, with checksum external to verified bytes.
4. **Package Database:** physical representation of atomic published generation, global requirement/version registry, architecture catalog, immutable artifact references, and artifact-before-metadata publication order.
5. **Bootstrap dependency closure:** native toolchain and runtime inventory needed for both Build chroot and M4 bootable set, with explicit relationships and ownership.
6. **Manage transaction substrate:** minimal correct target-root installation with checksum, path ownership, dependency checks and durable installed state; fail safely on partial application.
7. **VM/install target:** one specific first VM firmware/partition/filesystem configuration; general hardware support deferred, GRUB/systemd boot mandatory.
8. **Acceptance fixtures:** M2 full temporary-environment replication, M3 complete managed Build-chroot package-closure reproduction, M4 complete bootable-manifest dependency-closure production/publication with isolated per-package builds and cache-resume tests, and M5 independently hosted M1 → M2 bootstrap plus native managed Build-chroot tests.

The M4 build-root strategy is **selected**: fresh per-package Manage-provisioned roots and the published repository as the durable artifact checkpoint/cache. The intended protection transition is also selected in principle: bounded host-write protection during M1 and pre-chroot M2, then controlled native chroot execution after an explicit readiness gate; exact commands, mount layouts and privilege mechanics remain open. Other decisions above remain open until explicitly resolved; no prototype defaults are implied. Resolve them in Planning before Build must rely on them; do not silently commit to Arch-derived recipe behavior, G1 database formats, tar layouts, or QEMU BIOS just because a prototype used them.

## Evidence and validation strategy

- For M1–M2, retain machine-readable input, source checksum, environment, stage, runtime linkage, isolation, and failure evidence.
- For M3–M4, retain published package identities and integrity, database generation, Manage-installed closure and file inventory, and successful independent builds.
- For M5, retain installer commands, selected VM target, installed package state, GRUB/systemd boot marker, cloned repository revision, Distro-as-host qualification, fresh M1 and M2 source/toolchain/self-replication evidence, and a verified package built from a freshly assembled managed chroot within the VM.
- Include negative checks for host contamination, modified source/artifact checksums, incomplete generation publication, ownership conflicts, invalid dependency closure, and inability to form an independent Build chroot.
- Bind each active mechanical requirement to concrete registered product Validation tasks during Build. A successful mechanical run does not replace semantic review.

## Prototype evidence, not design authority

`proto/distro-bootstrap-chroot` informs host qualification and staged toolchain work; `proto/lfs-optimize` informs native construction and validation; `proto/g1-chroot`, `proto/g1-bootable`, and `proto/g2-installer` inform package, boot and install proofs; `proto/builder-discovery` and `proto/maint-lifecycle` inform source/recipe discovery and correction; `proto/bootstrap-staging` informs early staging methods. Reuse compatible mechanisms selectively without inheriting superseded semantics.
